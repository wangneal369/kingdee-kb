# KingdeeKB 多轮代码审查

审查不是一次通读。**每个 Pass 只看一个维度**，逐 Pass 记录发现；全部 Pass 结束后统一核实、去重、出报告；修复后进入下一轮复审，直到没有 P0/P1。

项目约定的权威来源（审查依据）：
- 开发约定：`.claude/skills/kingdee-kb-dev/SKILL.md`
- 编码规范：`OpenSpec/coding-standards.md`（Rust 规则 ID 见 `OpenSpec/rust-guidelines/safe-guides/`）
- 领域与不变量：`OpenSpec/project.md`
- 分维度检查清单：[references/checklists.md](references/checklists.md)

## 严重级别

| 级别 | 含义 | 是否阻断 |
|---|---|---|
| P0 | 数据损坏/丢失、跨项目数据泄露、凭据泄露、崩溃、命令不可用 | 阻断 |
| P1 | 功能错误、回归、锁/并发缺陷、错误被静默吞掉、契约不一致 | 阻断 |
| P2 | 违反项目约定、可维护性问题、缺测试、性能隐患 | 建议本轮修 |
| P3 | 风格、命名、注释、可读性 | 可选 |

## 第 0 步：确定范围（每轮开始都做）

1. 确定审查目标：默认 `git diff`（工作区）+ `git diff --cached`；用户给出 commit / 分支 / PR 时用 `git diff <base>...<head>`。
2. 列出改动文件，按层归类：`commands/` / `services/` / `app_state.rs` / `lib.rs` / `error.rs` / `resources/prompts/` / `capabilities/` / `src/lib/` / `src/contexts/` / `src/pages/` / `src/components/` / 测试 / 配置。
3. 对每个改动的函数/组件，**读完整上下文**（不只看 diff 行）：调用方、被调用方、对应的另一端（Rust ↔ TS）。
4. 判断改动级别：若属于新能力 / 跨模块重构 / 破坏性变更 / 安全策略，检查是否有对应 `OpenSpec/changes/<id>/`，没有则记一条 P2「缺提案」。
5. 写出本轮范围摘要（文件数、涉及层、风险最高的 3 处），再进入 Pass。

改动很小（≤3 个文件且单层）时，可合并 Pass，但 Pass 3（正确性）和 Pass 4（并发与错误）不得省略。

## 第 1–7 步：单维度 Pass

逐个执行，每个 Pass 开始时声明「Pass N：<维度>」，只记录该维度的发现，格式：

```
[Pass N][P?] 文件:行号 — 问题一句话
  触发条件：具体输入/状态 → 错误结果
  依据：规则/不变量/代码证据
```

| Pass | 维度 | 核心问题 |
|---|---|---|
| 1 | 架构与分层 | 逻辑放对层了吗？command 是否变胖、页面是否裸 `invoke`、模块导出与注册是否完整 |
| 2 | 前后端契约 | 命令是否在 `generate_handler!` 注册、TS 封装/类型与 Rust 结构体一致、参数名大小写、错误码、e2e mock |
| 3 | 业务正确性与数据 | `project_id` 隔离、候选/正式内容不变量、事务原子性、SQL、边界条件、缓存一致性 |
| 4 | 并发、异步与错误处理 | 持锁跨 await、锁顺序、spawn 未监控、`unwrap`/`panic`、静默吞错、取消与状态复位 |
| 5 | 安全与隐私 | 凭据存储、日志/错误泄露密钥、脱敏、路径与文件操作、`capabilities` 权限、XSS |
| 6 | 前端质量 | Hooks 依赖、状态不可变、key、懒加载、Context 单例、加载/空/错误态、a11y |
| 7 | 规范、性能与测试 | 编码规范、日志、dead code、O(n²)、大数据量、测试覆盖、注释与文档同步 |

每个 Pass 的完整检查项见 [references/checklists.md](references/checklists.md)。每个 Pass 结束写一行「Pass N 完成：发现 X 条（P0 a / P1 b / …）」，没有发现也要写。

## 第 8 步：自动化验证

按改动层运行（只跑相关的，耗时命令放后台）：

```bash
npm run typecheck
npm run lint
npm test
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml <相关模块>
```

失败项作为发现记录（编译/类型错误为 P0/P1，clippy/lint 警告为 P2/P3）。未运行的命令在报告中写明「未运行」及原因，不得写成通过。

## 第 9 步：发现核实（去误报）

对 Pass 1–8 的每条 P0/P1/P2 发现逐条复核：
1. 回到代码确认问题真实存在（不是 diff 视角的误读，调用方没有别处兜底）。
2. 写出可复现的触发场景；写不出的降级或标记「待确认」。
3. 合并同根因的重复发现，保留最严重级别。
4. 区分「本次改动引入」与「存量问题」；存量问题单独列，不阻断本次。

## 第 10 步：输出报告

```markdown
## 审查报告 — 第 N 轮

**范围**：<diff 目标>，<文件数> 个文件（后端 x / 前端 y）
**结论**：❌ 有阻断问题 / ⚠️ 可合入但建议修复 / ✅ 通过

### 阻断（P0/P1）
1. [P1] `path:line` 问题 — 触发场景 — 修复建议

### 建议（P2）
### 可选（P3）
### 存量问题（非本次引入）
### 验证结果
| 命令 | 结果 |
### 各 Pass 统计
| Pass | P0 | P1 | P2 | P3 |
```

报告用中文；问题按严重级别排序；每条给出具体修复建议，不只说「有问题」。

## 第 11 步：修复与多轮复审

1. 未经用户同意不改代码；用户要求修复时，按 P0 → P1 → P2 顺序修，每修一处说明对应哪条发现。
2. 修复后开始**第 N+1 轮**，重新从第 0 步执行，但范围为：
   - 上一轮所有 P0/P1/P2 发现对应位置 —— 逐条确认已修复（✅ 已修 / ❌ 未修 / ⚠️ 部分修）；
   - 本轮修复产生的新 diff —— 完整跑 Pass 1–7，重点查「修 A 坏 B」的回归；
   - 修复触及的调用方。
3. 复审报告额外包含「上轮发现追踪」表。
4. **终止条件**：某一轮 P0/P1 为 0 且上一轮阻断项全部 ✅；或已进行 3 轮仍有阻断项 —— 此时停止叠补丁，向用户说明现象、已排除项和下一步选项（遵循 `CLAUDE.md`「连续失败 3 次」规则）。

## 纪律

- 证据优先：每条发现都要有代码位置和触发场景，不凭印象。
- 不扩大范围：审查只针对目标 diff 及其直接影响面；顺手看到的存量问题放「存量」一节。
- 不擅自 commit / push / 改配置文件；删除任何文件前须用户确认。
